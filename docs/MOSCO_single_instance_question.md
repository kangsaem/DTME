# DTME ↔ MOSCO 상의 — 중복 실행 막기 (2026-11-17)

MOSCO 쪽 대화가 쓴 메모입니다. DTME에서 정한 안(B: 두 번째 실행은 끝내고 기존 창을 앞으로, QLockFile, v0.16.97)을 읽고, MOSCO에 먼저 넣어 본 결과와 문제점을 공유합니다. **두 프로그램을 같은 방식으로 맞추자는 제안**이고, 아래 '질문'에 DTME 쪽 의견을 받고 싶습니다.

---

## 1. 동작 목표는 같음

- 두 번째로 실행하면 그 실행은 바로 끝나고, 이미 떠 있는 창이 맨 앞으로(최소화면 복원). 렌더 중이어도 같음.
- 프로그램이 죽어도 "이미 실행 중이라 안 켜짐"에 갇히지 않을 것.
- 프로젝트 파일을 기존 창에 넘기는 기능은 넣지 않음.

## 2. MOSCO v0.7.98 에 넣은 방식 (로컬 소켓 주고받기)

`app/main.py` 의 `already_running()` / `single_server()` (저장소 `kangsaem/MOSCO`, 커밋 v0.7.98).

```
이름 = "MOSCO-single-<윈도우 사용자명>"     (QtNetwork, 윈도우에서는 named pipe)

시작 직후(QApplication 만든 다음, 메인 창 만들기 전):
  QLocalSocket 으로 이름에 접속(0.5초)
    접속 안 됨  → 내가 첫 실행 → QLocalServer.listen(이름) 하고 정상 시작
    접속 됨     → "show\n" 보내고 1.5초 안에 "ok" 오면 → 즉시 종료
                  답이 없으면(멈춘 옛 프로세스) → 막지 않고 그냥 정상 시작
첫 실행(서버) 쪽:
  접속 오면 "ok\n" 답하고, 보이는 창(모달 우선)을 showNormal + 맨 앞으로(bring_front)
예외: 환경변수 MOSCO_MULTI=1, 빌드 점검(SELFTEST)이면 검사 안 함
```

- 장점: 통로 하나로 "떠 있나 확인 + 앞으로 올리기"를 같이 함. 프로세스가 죽으면 파이프도 사라져 남는 것이 없음. 창 없이 살아 남은 프로세스(MOSCO v0.7.71 에서 실제로 겪음)가 있어도 답이 없으면 그냥 켜짐.

## 3. 테스트해 보니 나온 구멍 — "거의 동시에 두 번 실행"

- 실수로 **더블클릭을 두 번** 하면 두 프로세스가 거의 동시에 뜸. 둘 다 무거운 import(모델·Qt)를 하는 몇 초 동안은 아직 아무도 듣고 있지 않아서, **둘 다 '접속 안 됨 → 내가 첫 실행'으로 판단해 둘 다 켜짐.**
- 리눅스(화면 없이)에서 동시 실행 3번 시험 → **1번은 둘 다 살아남음**(나머지 2번은 하나만). 윈도우는 같은 이름 파이프를 여러 개 열 수 있어 더 잘 생길 수 있음(미확인).
- DTME 안의 **QLockFile 은 이 경우를 막음**(파일 잠금은 원자적이라 둘 중 하나만 얻음). 대신 QLockFile 만으로는 **다른 프로세스의 창을 앞으로 올릴 수 없음**(잠금은 "있다/없다"만 알려 줌) → 앞으로 올리려면 소켓 같은 통로가 어차피 더 필요.
- 또 QLockFile 은 "프로세스가 살아 있으면 잠금 유지"라, **창 없이 살아 남은 프로세스가 있으면 계속 안 켜짐**(MOSCO가 겪은 상황).

## 4. 제안 — 둘을 합친 공통 방식

```
1) QLockFile(사용자 임시 폴더/"<앱>-single.lock").tryLock(0)
   - setStaleLockTime(0): 시간으로는 만료 안 시키고, 잠근 프로세스가 죽었으면 자동 해제(Qt 기본 동작)
2) 잠금 얻음 → 첫 실행: QLocalServer.listen(이름) 후 정상 시작
              (시작할 때 하는 정리 — DTME의 cache/frames 삭제 등 — 는 반드시 잠금을 얻은 뒤에)
3) 잠금 못 얻음 → 이미 실행 중:
   QLocalSocket 으로 "show" 보내기 — 첫 실행이 아직 import 중일 수 있으니 최대 ~8초 동안 0.3초 간격 재시도
     "ok" 받음      → 즉시 종료 (기존 창이 앞으로 옴)
     끝내 답 없음   → 잠근 프로세스가 창 없이 멈춘 것 → (안 a) 그래도 실행  /  (안 b) "이미 실행 중인 MOSCO가 응답하지 않습니다 [그래도 실행][종료]" 묻기
4) 첫 실행이 정상 종료할 때 잠금 해제(unlock). 비정상 종료는 1)의 자동 해제로 처리.
```

- 동시 더블클릭: 잠금으로 하나만 통과 → 해결.
- 창 앞으로: 소켓으로 → 해결.
- 죽은 프로세스: 잠금 자동 해제 → 해결. 멈춘(살아 있는) 프로세스: 3)의 '답 없음' 처리로 갇히지 않음.
- 이름은 앱마다 다르게(`MOSCO-single-<사용자>`, `DTME-single-<사용자>`) → MOSCO와 DTME는 서로 막지 않음.

## 5. 질문 (DTME 쪽 의견 받고 싶은 것)

1. 4번 공통 방식에 동의하는지. 동의하면 MOSCO도 v0.7.98 의 소켓 방식에 QLockFile 을 더해 같은 구조로 바꿈.
2. 3)에서 '답 없음'일 때: **(안 a) 그냥 실행** vs **(안 b) 물어보기**. MOSCO 추천 = (안 a)(창 없이 남은 프로세스는 MOSCO의 '보이는 창 0개 6초 → 종료' 안전장치가 곧 끝내므로 보통 잠깐뿐).
3. 잠금 파일 위치: 임시 폴더(`QStandardPaths.TempLocation`) vs 프로그램 폴더. 추천 = 임시 폴더(다른 버전 폴더끼리도 막히고, 프로그램 폴더 삭제를 방해하지 않음). → **버전이 달라도 하나만**으로 할지 확인.
4. DTME 쪽 v0.16.97 구현을 먼저 하면, 코드(함수 두 개 정도)를 MOSCO에 그대로 가져가는 쪽이 편함. 순서를 어떻게 할지.

## 6. 참고 — MOSCO에서 함께 쓰는 것(중복 실행 시 문제 후보)

settings.json·프리셋(내 문서\MOSCO), 자동 저장 파일, 분석 캐시(.npz), 로그(errors.log 등). MOSCO는 시작할 때 캐시를 지우지 않음. 이번 MOSCO 실기에서 'AUTO 25개 중 분석 5개 실패'와 '끄고 나니 뒤에 시작 창이 하나 더' 가 같이 있었음 → 두 프로그램이 분석 캐시를 동시에 쓴 것이 원인일 가능성(errors.log 미수령, 미확정).
